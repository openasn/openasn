# Security Policy

## Data errors are not vulnerabilities

The most common report we get is "this IP classifies wrong". **That is a data
issue, not a security issue** — please use the
[data correction template](.github/ISSUE_TEMPLATE/data-correction.yml) instead,
where a curator will see it.

That includes: a VPN or hosting ASN we have not labelled yet, a residential
network mislabelled as infrastructure, a provider that moved its ranges, a
proxy or VPN service OpenASN fails to detect, and residential-proxy traffic in
general. None of these are vulnerabilities, because OpenASN does not claim to
catch them. From the README, in bold, on purpose:

> **A clean or `residential_isp` verdict is absence of evidence, not proof of
> innocence.** OpenASN is a first line of defense, not a fraud engine.

An evasion is only a vulnerability here if it works by *attacking the project* —
poisoning the build, tampering with a release, or exploiting a client — rather
than by simply being a network we do not know about yet.

## Reporting a vulnerability

Use **GitHub private vulnerability reporting**: the *Report a vulnerability*
button under this repository's **Security** tab
(<https://github.com/openasn/openasn/security/advisories/new>). It creates a
private advisory only the maintainers can see, so nothing is public while we fix
it. If that is unavailable to you, contact the maintainer
([@rameerez](https://github.com/rameerez)) privately through GitHub, or open a
public issue that says only *"I need a private channel for a security report"* —
with **no details** in it — and we will open one.

**Please do not** report vulnerabilities in public issues, in pull requests, or
in comments on unrelated threads.

Include, as far as you can: what you found, where (repo, file, workflow, client
and version, release tag or `build_id`), how to reproduce it, and what an
attacker gets out of it. A concrete reproduction is worth more than a scanner
finding.

**What to expect.** This is a small project: we aim to acknowledge a report
within 7 days and to tell you honestly whether we consider it a vulnerability,
what we plan to do, and roughly when. We will credit you in the advisory unless
you would rather stay anonymous. There is no bug bounty. Please give us a
reasonable window to ship a fix before publishing.

## In scope

Anything that lets someone get bytes, code, or a false claim of provenance into
a consumer of this project:

- **The build and release path** — the nightly workflow and any other workflow
  in `.github/workflows/`: injection into a job, secret exposure, an unpinned or
  hijackable action, a way to publish an artifact that did not come from a clean
  build, or a way to defeat the license-pin, cross-check, delta, drift,
  round-trip or spot-panel gates.
- **The published artifacts and their integrity metadata** — a crafted upstream
  input that makes the packer emit malformed bytes, or a mismatch between what
  `manifest.json` / `SHA256SUMS` claim and what is actually in a release.
- **`scripts/lint_overrides.rb`** — it parses untrusted contributor input in CI.
- **Client parsing of the artifacts or of Tier B lists.** A Tier B list is
  fetched from a party this project does not control, so a client must treat it
  as untrusted input: crashes, memory blowups, path traversal, or following a
  redirect to a non-HTTP scheme all count. Client bugs are best filed in the
  client's own repo (for example
  [`openasn/openasn-ruby`](https://github.com/openasn/openasn-ruby)) using the
  same private channel; if you are unsure which repo owns it, report it here and
  we will route it.
- **The Tier B recipe itself** (`fetch-manifest.json`) — a recipe that points a
  fetching client somewhere it should not go.

## Out of scope

- Wrong, missing or stale classifications — see the top of this file.
- The inherent limits documented in the README: no residential-proxy detection,
  no IPv6 overlay parity guarantee, nightly-cadence freshness, and the fact that
  clients must fetch Tier B lists themselves.
- Vulnerabilities in upstream data sources or in the third-party lists a client
  fetches. Report those to their maintainers; tell us too if it affects how a
  client should treat that source, and we will adjust the recipe or the guidance.
- Reports generated by a scanner with no demonstrated impact on this project.
- Anything that requires an attacker to already control the machine running the
  client, or the contents of your own data directory.

## Verifying what you run

Every release ships `SHA256SUMS`, and `manifest.json` carries a per-file SHA-256
plus the upstream URL, license, license-file hash and fetch time for every source
that went into the build. Upstream license texts are SHA-256-pinned in
`data/licenses/` and the build fails loudly if any of them changes. Always
download through the tag-addressed URL
(`releases/download/latest/<file>`), never the "Latest" badge form, and check the
hashes — if bytes you downloaded do not match the manifest, that is exactly the
kind of report this policy is for.
