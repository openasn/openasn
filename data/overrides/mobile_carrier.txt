# mobile_carrier.txt — ASNs of DEDICATED cellular carrier networks.
#
# Effect: sets flags bit 10 (mobile_carrier). Classification: :mobile
# (precedence rule 11). :mobile is a likely_human verdict; its value is
# telling apps "one IP here = hundreds of humans behind carrier NAT — never
# hard-block, never per-IP rate-limit aggressively".
#
# Curation bar (deliberately strict for the seed):
#   * The ASN carries a carrier's MOBILE subscriber traffic specifically —
#     not a converged telco ASN mixing fixed broadband on the same AS
#     (those stay :residential_isp, which is equally likely_human, so a
#     miss here costs almost nothing).
#   * Fixed-wireless ISPs (WISPs) do NOT belong here: their subscribers are
#     homes with stable IPs — that's :residential_isp, not carrier NAT.
#   * Known incompleteness is fine; recall grows via PRs. Misclassified
#     entries are the only real bug class for this file.
# Evidence: ipverse as-metadata org descriptions
# (https://raw.githubusercontent.com/ipverse/as-metadata/master/as.json),
# checked 2026-07-04, selected via
# `rake overrides:candidates` keyword sweep + manual review.

# ============================ Sweep 2026-09-12 (N1) ============================
# Four corrections found by an adversarial audit of this file against the RIRs' own RDAP records
# (the file had been curated from ipverse org DESCRIPTIONS, which is exactly the trap the cdn.txt
# header warns about: a description string identifies the legal HOLDER, not the network).
#
# 1. AS133481 REMOVED, AS131445 ADDED (a swap). Advanced Wireless Network Co. Ltd is the legal
#    holder of BOTH of AIS Thailand's ASNs, so both carry the identical ipverse description
#    "ADVANCED WIRELESS NETWORK COMPANY LIMITED" and the seed picked the wrong one. APNIC RDAP is
#    unambiguous: AS133481 is aut-num "AIS-Fibre-AS-AP" with the remark "AIS Fibre" - AIS's FIXED
#    FTTH network (553,216 IPv4 addresses over 610 prefixes, 7.32M APNIC end users), and it was
#    answering :mobile for Thai home fibre subscribers. AS131445 is aut-num "AIS3G-2100-AS-AP" -
#    the dedicated cellular network - and it was answering :residential_isp. An exact inversion.
#    AS133481 needs no override: ipverse already categorizes it isp, so it now answers
#    :residential_isp on its own. src: https://rdap.apnic.net/autnum/133481 +
#    https://rdap.apnic.net/autnum/131445 (2026-09-12)
#
# 2. AS138407 and AS139080 REMOVED - both are DATACENTERS, not cellular networks. Their APNIC
#    aut-num remarks say so verbatim: "The Internet Data Center of Guizhou Mobile Communication
#    Company Limited" (CMNET-GZIDC-CN) and "...of Sichuan Mobile Communication Company Limited"
#    (CMNET-SCIDC-CN). :mobile is a likely_human, never-hard-block verdict; asserting it over
#    datacenter space is a false negative in the direction that costs an abuse-policy consumer
#    the most. Both moved to hosting_extra.txt. src: https://rdap.apnic.net/autnum/138407 +
#    https://rdap.apnic.net/autnum/139080 (2026-09-12)
#
# 3. AS6854 REMOVED - "PJSC MegaFon" is the holder, but the aut-num is SYNTERRA-AS and the RIPE
#    record is a transit map (UpStreams / regional Peering / Customers / BGP communities for
#    transit peers). rDNS across its space is backbone router naming - D1-MCH-gi0-1.314.main.
#    synterra.ru, MSK-D1-DUB-gi1-0-0.76.main.synterra.ru - and APNIC measures 0 end users behind
#    it. This is MegaFon's ex-Synterra fixed backbone, not its cellular subscriber network.
#    src: https://rdap.db.ripe.net/autnum/6854 + rDNS of 83.222.192.1 / 83.222.208.1 (2026-09-12)
#
# KNOWN, DELIBERATELY LEFT: AS10728, AS11461, AS5079 (T-Mobile USA) and AS140895 (China Mobile
# Anhui) currently announce no address space, so their lines change no verdict. They are kept as
# hedges in case the ASNs are re-activated; they cost nothing because a flag with no ranges is
# never consulted.
#
# NOT AUDITED THIS PASS: the file's recall. mobile_carrier is 40 lines against a world of
# several hundred dedicated cellular ASNs; a ranked candidate list (routed ASNs with >=300k APNIC
# end users and a cellular-looking name, none of them yet in any override file) is the input for
# the next expansion. Known incompleteness is fine per the header; misclassification is not.

# ======================= Sweep 2026-09-12 (P3-C) — worldwide expansion =======================
# WHAT WAS DONE. The 175 highest-impact candidates worldwide (the 15 "dedicated-cellular pins"
# named in eyeball_confirm.txt's header, the 66 keyword-flagged routed ASNs with >=300k APNIC end
# users, and a brand sweep over every routed ASN with >=800k users) were ranked by measured
# eyeball population and researched per record: RDAP for the aut-num, a CENSUS of the INETNUM
# netnames inside the ASN's own announced space, live rDNS at prefix midpoints, PeeringDB, and the
# operator's own product pages. An independent pass then re-derived every line below from the
# registry or from live rDNS before it shipped.
#
# THE METHOD THAT MATTERS, for whoever extends this file next. The aut-num record alone is not
# enough and the org DESCRIPTION is actively misleading (it names the legal holder, not the
# network - the trap that produced the AIS inversion). What decides it is the netname census:
#   cellular  -> *_APN_*, *-GPRS-*, *-UMTS-*, *-3G-*, *-LTE-*, *-Subscribers-*
#   CONVERGED -> *-FIXED-DATA*, *FTTH*, *DSL*, *PPPoE*, WiMAX, *Leased Line*, *Enterprise*, *B2B*
# and one converged block anywhere in the AS is a rejection, however many mobile blocks sit beside
# it. Query it with `https://rdap.org/ip/<first address of a prefix the ASN announces>`, and sample
# MANY prefixes: Orange Maroc AS36925 shows `Mobile_Costumers` on its four largest blocks and is
# still a REJECT, because 41.87.128.0/20 in the same AS is "Dynamic DSL Orange Maroc Customers".
#
# THE RESULT IS MOSTLY REJECTIONS, and that is the bar working as designed. Of the top 60 ASNs on
# Earth by eyeball population, 32 were rejected as converged, fixed, backbone or datacenter
# networks. Named here so nobody re-proposes them: AS9808 China Mobile and the seven provincial
# CMNET cores (AS56046 Jiangsu, AS24400 Shanghai, AS56048 Beijing, AS24445 Henan, AS56045 Jiangxi,
# AS56044 Liaoning, AS56040 Guangdong - each aut-num describes the province's whole IP CORE
# NETWORK and the shared CMNET inetnum declares both "Mobile Communications Network Operator in
# China" and "Internet Service Provider in China"; AS24400's descr names Oriental Cable Network,
# AS56048 announces 211.151.96.0/19 CHINA-21VIANET, AS56046 announces 45.250.28.0/22 Duchuang-IDC);
# AS33771 Safaricom Kenya (SAFARICOM-FIXED-DATA in its own space); AS9534 Maxis; AS18001 Dialog;
# AS20294 MTN Uganda (Wimax-clients); AS43766 Zain KSA (RYD-FTTH); AS26615 TIM Brasil; AS38623
# Metfone (dynamic-ip-adsl.metfone.com.kh); AS812 Rogers (cpe.net.cable.rogers.com); AS5650
# Frontier; AS4230 Embratel and AS4713 OCN (a backbone and a fixed fibre ISP held by mobile
# groups); AS24560 AIRTELBROADBAND-AS-AP "Telemedia Services"; AS4761 Indosat; AS4775 Globe
# Telecom (BAYAN-DSL-PPPoE-AP); AS36925 Orange Maroc; AS35819 Mobily (Broadband IP Range on every
# sampled prefix); AS2518 BIGLOBE; AS36935 + AS24835 Vodafone Egypt; AS10139 SmartBro (a WISP);
# AS63023 GTHost (a VPS host, not a carrier at all - a hosting_extra lead instead).
#
# THREE OF THE FIFTEEN SEED PINS DID NOT SURVIVE. eyeball_confirm.txt's header offers 15 ASNs as
# an "authoritative seed"; it is a lead list, not an authority. AS4818 (DiGi/CelcomDigi) is
# aut-num DIGIIX-AP "DiGi Internet Exchange" and CelcomDigi's own PeeringDB record says "We are
# mobile and fixed operator in Malaysia" (info_type Cable/DSL/ISP). AS12252 (Claro Peru) carries
# LACNIC registrant handle PE-TPSA4, Telmex Peru - the FIXED company America Movil absorbed.
# AS44244 (MTN Irancell) has empty RIPE remarks, only untyped city pools, and positive
# counter-evidence (2.145.192.0/18 Colo-Reserved, 85.185.36.0/22 MTN-Irancell-Datacenter-Services)
# plus a TD-LTE fixed-wireless home product. All three keep their eyeball_confirm pin.
#
# NOTE ON PRECEDENCE (classifier.rb): FLAG_BAD_ASN | FLAG_HOSTING_EXTRA | FLAG_CDN and
# category == "hosting" are all tested BEFORE FLAG_MOBILE, while category == "business" is tested
# AFTER it. So a line here is a silent no-op on a `hosting`-categorized ASN unless corrections.yml
# fixes the category too, and it works fine on a `business`-categorized one. AS29465 MTN Nigeria
# is the standing example: it is in brianhama/bad-asn-list, so it answers :hosting whatever we do.
